# Day 8 Reflection

**The most difficult concept.** The hardest concept for me was concurrency, in particular understanding why two requests that each look correct on their own can break things when they run at the same time. The "check if the seat is free, then book it" idea seemed obviously fine until I realized another user could slip in between the check and the write. I overcame it by slowing down and tracing two users through the code step by step on paper, then trying the same scenario with transactions and an atomic `UPDATE ... WHERE status = 'available'`. Seeing exactly one request win and the other get zero rows affected made it click. Adding a UNIQUE constraint as a safety net also showed me that the database can enforce rules even when my code has bugs.

**What I would improve in my capstone.** Based on the feedback I received, I would improve how I explain and justify my design decisions, not just list them. My reviewers pointed out that I described components without always saying why I picked them or what the alternatives were. I would add clearer trade-off sections, back my choices with numbers from my traffic estimates, and test my design against failure cases such as a server crashing mid-payment.

**What I will learn next.** Next I want to learn more about databases in depth, especially indexing, query performance, and replication, followed by caching strategies and message queues. I also want to build a small version of TicketHub myself, including a waiting room and a seat-hold endpoint, so I can see how these ideas behave under real load rather than only on paper.
